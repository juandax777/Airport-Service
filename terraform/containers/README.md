# ECS Fargate y entrada web

Esta fase declara tres servicios en subredes privadas, con imágenes Linux x86-64 de ECR fijadas por digest. Web App recibe peticiones desde el ALB y llama a `airport-service:8000` e `itinerary-service:8000` mediante Service Connect. Itinerary también llama a Airport por esa red. Solo Airport consulta API Colombia. El ALB reenvía tráfico HTTP en la demo de `dev`. Cuando configuras HTTPS, reenvía tráfico por el puerto 443 y redirige el 80 al dominio configurado. Su destino único es Web App, con comprobación HTTP en `/health/live`.

Configura `compute.allowed_web_cidrs` con las IPv4 públicas del equipo, preferiblemente una entrada `/32` por IP. El balanceador limita los puertos 80 y 443 a esas redes. El CRUD es compartido entre quienes tengan acceso, así que usa datos ficticios en `dev`.

## Preparar un despliegue autorizado

1. Habilita primero backend, ECR, red y servicios de datos. Completa el [aprovisionamiento y las migraciones](../operations/README.md) desde un ejecutor privado antes de habilitar ECS.
2. Construye cada imagen usando su carpeta de servicio como contexto. Directorios `services/web_app`, `services/airport_service` e `services/itinerary_service`. Usa `--platform linux/amd64` y para Itinerary usa además `--build-arg INCLUDE_RDS_CA=true`. El flujo existente de publicación prepara estas variantes y solo se ejecuta cuando `AWS_DEPLOY_ENABLED` está habilitado. Una vez publicada cada imagen bajo autorización, copia el digest `sha256:...` de ECR al objeto `compute.image_digests`.
3. Carga dos secretos de texto en Secrets Manager. El primero es `DATABASE_URL` para `itineraries_app`, con el host privado de RDS y `?sslmode=verify-full`. El segundo es `RABBITMQ_URL` para el publicador, usando AMQPS y el vhost `/`. Codifica las credenciales como componentes de URL. Terraform recibe solo los ARN. Si los secretos usan claves KMS propias, agrega sus ARN a `secrets_kms_key_arns` y verifica que sus políticas permitan descifrado al rol de ejecución de Itinerary.
4. En `dev` puedes usar el DNS del ALB sin configurar un dominio. Si vas a usar HTTPS, configura `hostname` y un certificado ACM emitido en la región del ALB. Si esta raíz debe administrar el registro de Route 53, suministra `hosted_zone_id`. Para DNS externo, apunta el dominio al DNS del ALB que devuelve `compute`.
5. Revisa el plan del entorno. Comprueba tareas saludables, mapa y CRUD desde la `web_url` que devuelve `compute`. En modo HTTPS, comprueba también la redirección desde HTTP. Verifica que Airport e Itinerary carezcan de IP pública y que el rol de ejecución de Itinerary solo pueda leer sus dos secretos. Los logs de aplicación se escriben en `/ecs/<proyecto-entorno>/<servicio>`, con 14 días de retención por defecto.

La comprobación HTTP de los contenedores indica que el proceso responde. La conectividad a PostgreSQL y la publicación a RabbitMQ se verifican por separado mediante el flujo de creación de un itinerario. Para rotar secretos inyectados como variables, fuerza un nuevo despliegue. Para revertir una versión, vuelve a los digests anteriores y revisa la compatibilidad con las migraciones ya aplicadas. Si aparecen nuevos endpoints de Service Connect, vuelve a desplegar los clientes para que los resuelvan. [Service Connect](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect-concepts-deploy.html) · [Certificados TLS de RDS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.SSL.html).

Las tareas tienen 0.5 vCPU y 1 GiB para dejar capacidad al proxy. Dev usa una tarea por servicio. Ajusta `desired_count` a dos o más para distribuir réplicas entre zonas tras revisar capacidad y costo. Los roles de ejecución solo pueden descargar del ECR propio y escribir en los logs del servicio. Itinerary añade acceso a sus secretos. [Dimensionamiento del proxy](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect-concepts-deploy.html).
