# Notificaciones con Lambda

Terraform declara una función Python 3.12 en subredes aisladas. La función consume la cola `notifications` del vhost `/` mediante un event source mapping. El acceso a PostgreSQL usa el grupo de notificaciones y los endpoints privados de Lambda, STS y Secrets Manager permiten operar sin publicar el broker ni la función. Cada endpoint agrega costo por zona. Si la VPC ya tiene endpoints con DNS privado para estos servicios, coordina su gestión antes de aplicar. El endpoint de Secrets Manager también admite las conexiones de Itinerary y del ejecutor operativo, cuyos permisos de lectura siguen definidos por IAM. [Red para el mapping de Amazon MQ](https://docs.aws.amazon.com/lambda/latest/dg/process-mq-messages-with-lambda.html).

1. Desde el ejecutor privado, aplica las migraciones de `notifications`, incluida `002_quarantine.sql`, y prepara el exchange, la cola y el usuario consumidor según la [guía de operaciones](../operations/README.md).
2. Prepara los dos secretos. El de la base contiene la URL SQLAlchemy de `notifications_app` con `postgresql+psycopg` y `sslmode=verify-full`. El del broker contiene el objeto JSON con `username` y `password` del consumidor. Terraform recibe los ARN. Si usas claves KMS administradas por el equipo, incluye sus ARN y autoriza el rol en las políticas de clave.
3. Construye la imagen con `Dockerfile.lambda` y el contexto `services/notification_service`. Workflow y build manual deben usar Linux AMD64 y desactivar la atestación de procedencia de la imagen. Usa el digest de la imagen Lambda una vez publicada en el repositorio de notificaciones bajo autorización. [Imágenes Python para Lambda](https://docs.aws.amazon.com/lambda/latest/dg/python-image.html).
4. Activa el objeto `notification_worker` con `enabled = false` para preparar la función y las alarmas. Habilita el mapping solo después de confirmar que las migraciones y credenciales están listas. Si hay un consumidor en contenedor conectado a esa misma cola, detenlo antes del cambio. Compose usa su propio broker y Dockerfile.
5. En la validación autorizada, publica un itinerario y comprueba la fila en `notifications`. Repite el mismo evento para verificar que hay una sola fila. Envía un mensaje inválido y comprueba la cuarentena y su alarma. Configura `alarm_actions` con un destino de alertas aprobado si quieres recibir avisos de CloudWatch.

El handler decodifica Base64, conserva compatibilidad con `data.id` y registra como máximo una fila por `event_id` mediante una inserción atómica. Si el mensaje es inválido, conserva su envoltorio en `notification_quarantine` antes de confirmar el lote. Restringe el acceso a esa tabla y define su retención. Puede contener información personal. Los logs solo incluyen una marca de cuarentena, sin copiar el mensaje. Si falla PostgreSQL o la infraestructura, la función devuelve un error y Lambda reintenta el lote. Revisa los límites de entrega y el tiempo de retención del broker antes de producción. [Reintentos de Amazon MQ](https://docs.aws.amazon.com/lambda/latest/dg/with-mq.html).

El grupo de logs conserva 14 días y tiene alarmas para errores, limitación de invocaciones y cuarentena. RabbitMQ 4 no publica métricas individuales de cola con las dimensiones anteriores de CloudWatch. Consulta la profundidad de `notifications` por la API de gestión desde el ejecutor privado. Para rotar el secreto de PostgreSQL, inicia entornos Lambda nuevos después de actualizarlo, ya que la función reutiliza la conexión y la configuración entre invocaciones. [Métricas de RabbitMQ 4](https://docs.aws.amazon.com/amazon-mq/latest/developer-guide/rabbitmq-4.html).
